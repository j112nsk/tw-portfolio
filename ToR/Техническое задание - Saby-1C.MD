# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
**На разработку интеграционного сервиса «Robot»**

**Интеграция Saby (СБИС) → 1С:Бухгалтерия 3.0**
## 1. Общие положения
### 1.1. Основание для разработки

Необходимость автоматизации загрузки первичных документов из Saby в 1С для ведения бухгалтерского учёта.

### 1.2. Цель разработки

Обеспечить автоматическую ежедневную загрузку документов из Saby в 1С без участия пользователя.

### 1.3. Архитектура решения

Реализуется отдельный сервис:
- Наименование: Robot
- Тип: автономный интеграционный сервис
- Размещение: сервер Заказчика
- Запуск: планировщик Windows (1 раз в сутки)
- Обмен данными: XML-файлы
- Взаимодействие с 1С: через COM / HTTP / штатный механизм (уточняется подрядчиком)

## 2. Объект автоматизации
### 2.1. Перечень загружаемых документов

Из Saby в 1С подлежат загрузке:
1. Акт выполненных работ
2. Товарная накладная
3. Счёт-фактура

### 2.2. Объём нагрузки

- 50–100 документов в сутки
- Пиковая нагрузка: до 200 документов
- Обработка выполняется ночью

## 3. Функциональные требования
### 3.1. Общий алгоритм работы

Сервис должен:

1. Запускаться по расписанию.
2. Получать XML-файлы из заданного каталога.
3. Определять:
   - новые документы
   - ранее загруженные, но изменённые документы
4. Создавать или обновлять документы в 1С.
5. Формировать запись в журнале загрузки.
6. Архивировать обработанные файлы.
7. При ошибке одного документа — продолжать обработку остальных.

### 3.2. Логика загрузки
#### 3.2.1. Новые документы

Документ считается новым, если его идентификатор Saby отсутствует в 1С.

Результат:
- создаётся новый документ в 1С
- документ создаётся непроведённым

#### 3.2.2. Обновление документа

Если документ уже существует:

- выполняется обновление шапки
- выполняется полная перезапись табличной части
- проведение не выполняется

### 3.3. Требования к созданию документов
#### 3.3.1. Общие правила

- Номер переносится из Saby
- Дата переносится из Saby
- Организация — фиксированная (настраивается)
- Склад — фиксированный (один)

### 3.4. Сопоставление справочников
#### 3.4.1. Контрагенты

Поиск по:

- ИНН
- КПП

Если контрагент отсутствует:

- документ не создаётся
- фиксируется ошибка
- автоматическое создание запрещено

#### 3.4.2. Договоры

- Подбор по контрагенту
- Если несколько — используется основной
- Если отсутствует — ошибка

#### 3.4.3. Номенклатура

- Поиск по коду
- Если код не найден:
   - строка помечается как несопоставленная
   - документ создаётся
   - бухгалтер вручную выполняет сопоставление

Создание номенклатуры автоматически запрещено.

### 3.5. Журнал загрузки

В 1С должен быть реализован регистр (или документ) «Журнал интеграции».

Обязательные поля:

- Дата/время загрузки
- Тип документа
- Номер Saby
- Ссылка на документ 1С
- Статус:
   - Создан
   - Обновлён
   - Ошибка
- Текст ошибки
- Признак обновления

Срок хранения: 6 месяцев.

### 3.6. Обработка ошибок

Требования:
- Ошибка одного документа не должна останавливать сервис.
- Все ошибки фиксируются.
- Повторная автоматическая загрузка не выполняется.
- Повторный запуск сервиса не должен приводить к задвоению.

## 4. Нефункциональные требования
### 4.1. Производительность

- Обработка 100 документов — не более 30 минут.
- Время создания одного документа — не более 5 секунд.

### 4.2. Надёжность

- Сервис должен быть идемпотентным.
- При повторном запуске не создаются дубликаты.
- Уникальность обеспечивается хранением ID Saby в 1С.

### 4.3. Логирование

Robot должен вести:

1. Технический лог работы.
2. Лог ошибок.
3. Лог входящих файлов.

Формат логов — текстовый (UTF-8).

Срок хранения — 6 месяцев.

### 4.4. Требования к безопасности

- Использование отдельной технической учётной записи 1С.
- Доступ к каталогу сервиса ограничен правами ОС.
- Хранение настроек подключения в конфигурационном файле.

## 5. Требования к поставке

Подрядчик обязан предоставить:

1. Исполняемый файл сервиса.
2. Исходный код (если предусмотрено договором).
3. Инструкцию по установке.
4. Инструкцию по настройке.
5. Описание структуры XML.
6. Описание механизма обновления.
7. Инструкцию по резервному копированию.
8. Методика тестирования.

## 6. Тестирование и приёмка
### 6.1. Приёмочные сценарии

1. Загрузка нового акта.
2. Загрузка новой накладной.
3. Загрузка счёт-фактуры.
4. Обновление ранее загруженного документа.
5. Ошибка при отсутствии контрагента.
6. Ошибка при отсутствии договора.
7. Несопоставленная номенклатура.
8. Повторный запуск без задвоения.

### 6.2. Критерии успешной приёмки

Система считается принятой, если:

- 100% корректных документов загружаются без ошибок.
- Ошибки корректно фиксируются.
- Дубликаты отсутствуют.
- Производительность соответствует требованиям.

## 7. Границы ответственности
**Подрядчик отвечает за:**

- корректность алгоритмов загрузки
- идемпотентность
- журналирование
- документацию
- установку и первичную настройку

**Заказчик отвечает за:**

- предоставление тестовой базы 1С
- предоставление XML-образцов
- настройку планировщика Windows
- приёмочное тестирование

## 8. Ограничения

В рамках проекта НЕ реализуется:

- автоматическое создание контрагентов
- автоматическое создание номенклатуры
- проведение документов
- уведомления пользователям
- двусторонняя синхронизация
