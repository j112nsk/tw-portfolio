# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
**На разработку программы подписания отчетов ПФР**

## 1. Общие сведения
### 1.1. Наименование

Программа подписания XML-отчетов ПФР с использованием КЭП.

### 1.2. Назначение

Программа предназначена для:

- подписания XML-отчетов ПФР электронной подписью
- использования на рабочих местах сотрудников ПФР
- работы с внешними носителями (флеш-накопителями клиентов)

### 1.3. Интеграция с ПО

Используемые компоненты:

- КриптоПро CSP
- XML-файлы, сформированные в: Saby (СБИС), Контур, 1С:Бухгалтерия или любой другой учетной ситеме

## 2. Архитектура решения
### 2.1. Общая схема работы

1. Пользователь запускает программу
2. Выбирает XML-файл(ы) с флешки
3. Выбирает сертификат (из контейнера КриптоПро)
4. Программа выполняет подписание
5. Подписанные файлы сохраняются на флешке
6. Формируется лог операций

### 2.2. Требования к среде

- ОС: Windows 7 и выше
- Интернет: не требуется
- Установка: переносимый .exe (portable) не требует прав администратора

## 3. Функциональные требования
### 3.1. Выбор входных данных

Программа должна обеспечивать:

- выбор одного или нескольких XML-файлов
- поддержка только файлов формата .xml
- отображение списка выбранных файлов

### 3.2. Работа с сертификатами
#### 3.2.1. Источник сертификатов

- контейнеры КриптоПро, расположенные на внешнем носителе
- возможна работа с несколькими сертификатами

#### 3.2.2. Отображение сертификатов

При выборе сертификата программа должна отображать:

- ФИО владельца
- срок действия
- статус (действителен / просрочен)

#### 3.2.3. Проверка сертификата

Перед подписанием необходимо:

- проверить срок действия сертификата
- если сертификат просрочен: запретить подписание, вывести сообщение об ошибке

#### 3.2.4. Аутентификация
- при наличии PIN/пароля контейнера используется стандартное окно КриптоПро CSP
- реализация собственного ввода PIN не требуется

### 3.3. Подписание файлов
#### 3.3.1. Общие требования

- тип подписи: КЭП
- формат: отсоединённая подпись (.sig)

#### 3.3.2. Логика подписания
Для каждого файла:

1. выполняется подпись XML
2. создаётся файл подписи .sig
3. имя файла сохраняется без изменений

Пример:

>report.xml
>
>report.sig

#### 3.3.3. Пакетная обработка
- поддержка подписания нескольких файлов за один запуск
- обработка выполняется последовательно

### 3.4. Выходные данные
- подписанные файлы сохраняются в той же директории (на флешке)
- структура файлов не изменяется
- архивирование не выполняется

### 3.5. Журналирование

Программа должна формировать лог-файл:

- формат: .txt
- расположение: рядом с XML-файлами (на флешке)

#### 3.5.1. Содержимое лога

Для каждого файла:

- дата и время
- имя файла
- выбранный сертификат (ФИО)
- результат: успешно / ошибка
- текст ошибки (при наличии)

### 3.6. Пользовательский интерфейс

#### 3.6.1. Общие требования
- одностраничный интерфейс (single screen)
- минимальное количество действий

#### 3.6.2. Основные элементы
1. Кнопка «Выбрать файлы»
2. Список файлов
3. Выпадающий список сертификатов
4. Кнопка «Подписать»
5. Область статуса / сообщений

#### 3.6.3. UX сценарий
1. Пользователь выбирает XML
2. Выбирает сертификат
3. Нажимает «Подписать»
4. Получает результат

## 4. Обработка ошибок

Программа должна обрабатывать:
|          Ошибка          |         Поведение         |   |   |
|:------------------------:|:-------------------------:|---|---|
| Файл не XML              | Сообщение + пропуск       |   |   |
| Нет доступа к контейнеру | Ошибка                    |   |   |
| Неверный PIN / пароль    | Сообщение                 |   |   |
| Просрочен сертификат     | Запрет подписи            |   |   |
| Ошибка КриптоПро         | Логирование + продолжение |   |   |
| Повреждённый XML         | Ошибка                    |   |   |

## 5. Нефункциональные требования

### 5.1. Производительность
- время подписи одного файла — не более 2 секунд
### 5.2. Надёжность
- ошибка одного файла не останавливает обработку остальных
- повторный запуск не приводит к повреждению данных
### 5.3. Безопасность
- приватные ключи не копируются
- работа только через КриптоПро
- данные не передаются по сети
### 5.4. Логирование
- лог хранится на флешке

## 6. Требования к поставке
Подрядчик обязан предоставить:

1. Исполняемый файл (.exe)
2. Инструкцию пользователя
3. Инструкцию по установке
4. Описание поддерживаемых форматов подписи
5. Тестовые примеры

## 7. Критерии приёмки
Система считается принятой, если:

1. XML корректно подписывается
2. Формируется файл .sig
3. Поддерживается несколько файлов
4. Корректно работает выбор сертификата
5. Блокируется просроченный сертификат
6. Формируется лог
7. Программа работает без интернета
8. Не требует прав администратора

## 8. Ограничения

- Не выполняется валидация XML
- Не выполняется отправка в ПФР
- Не выполняется проверка структуры отчёта
- Не выполняется работа с архивами

## 9. Требования к формату электронной подписи

### 9.1. Общие требования

Подписание должно выполняться с использованием:

- квалифицированной электронной подписи (КЭП)
- криптопровайдера: КриптоПро CSP

### 9.2. Формат подписи

Используемый формат:

- CAdES-BES (CMS Advanced Electronic Signature – Basic Electronic Signature)

### 9.3. Тип подписи
- подпись: отсоединённая (detached)
- результат: отдельный файл .sig

### 9.4. Требования к формированию подписи

Для каждого XML-файла:

1. Формируется подпись в формате CAdES-BES
2. Используется исходный файл без изменений
3. Подписываемые данные: весь XML-файл целиком (binary mode)

### 9.5. Алгоритмы

Подпись должна использовать алгоритмы, поддерживаемые КриптоПро:

- ГОСТ Р 34.10-2012
- ГОСТ Р 34.11-2012

### 9.6. Состав подписи

Подпись должна содержать:

- сертификат подписанта
- данные подписи (SignedData)
- без включения времени штампа (TSP не требуется)

### 9.7. Совместимость

Результирующий файл .sig должен:

- корректно проверяться средствами КриптоПро CSP
- быть пригоден для загрузки в системы ПФР без дополнительной обработки

### 9.8. Ограничения
не требуется:
- CAdES-T
- CAdES-X
- архивные подписи
- не требуется проверка цепочки сертификатов онлайн (OCSP/CRL)

## 10. Требования к пользовательскому интерфейсу
### 10.1. Общие требования

Интерфейс должен быть:

- одностраничным (Single Screen)
- максимально простым
- рассчитан на неподготовленного пользователя

### 10.3. Элементы интерфейса
#### 10.3.1. Блок выбора файлов
- кнопка: «Выбрать файлы»
- поддержка множественного выбора
- отображение списка выбранных файлов

#### 10.3.2. Блок выбора сертификата
- выпадающий список сертификатов
- отображение:
   - ФИО владельца
   - срок действия

Пример:

> Иванов Иван Иванович | до 01.12.2026

#### 10.3.3. Индикация статуса сертификата
- действующий — доступен для выбора
- просроченный — отображается, но:
   - помечается как «Просрочен»
   - недоступен для выбора
10.3.4. Кнопка «Подписать»
активна только при:
выбранных файлах
выбранном валидном сертификате

#### 10.3.5. Область статуса

Должна отображать:

- текущий процесс (например: «Подписание файла 2 из 5»)
- результат:
   - успешно
   - ошибка

### 10.4. Поведение интерфейса
#### 10.4.1. Во время обработки
- кнопка «Подписать» блокируется
- отображается прогресс

#### 10.4.2. После завершения
- выводится итог:
   - «Подписание завершено»
   - или список ошибок

### 10.5. Обработка пользовательских ошибок

|         Ситуация        |    Поведение    |   |   |
|:-----------------------:|:---------------:|---|---|
| Не выбран файл          | Сообщение       |   |   |
| Не выбран сертификат    | Сообщение       |   |   |
| Просроченный сертификат | Блокировка      |   |   |
| Ошибка подписи          | Сообщение + лог |   |   |
|                         |                 |   |   |
