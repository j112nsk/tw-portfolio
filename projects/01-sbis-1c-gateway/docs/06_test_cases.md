# Тест-кейсы

## TC-01: Успешная отправка УПД (сценарий 1)

| Шаг | Действие                                                                                  | Ожидаемый результат                            |
|-----|-------------------------------------------------------------------------------------------|------------------------------------------------|
| 1   | 1С отправляет POST /documents/outgoing с валидным JSON                                    | Шлюз возвращает 202 Accepted, в теле requestId |
| 2   | Проверить БД шлюза                                                                        | Появилась запись со статусом pending           |
| 3   | Через некоторое время (после отправки в СБИС) запросить GET /documents/status/{requestId} | Статус sent или delivered                      |
|     |                                                                                           |

## TC-03: Сбой СБИС – очередь и повтор

| Шаг | Действие                                | Ожидаемый результат                                                          |
|-----|-----------------------------------------|------------------------------------------------------------------------------|
| 1   | Эмулировать недоступность API СБИС      | Шлюз фиксирует ошибку, документ остаётся в очереди                           |

|     |                                         |                                                                              |

## TC-05: Неверный токен аутентификации (401 Unauthorized)

| Шаг | Действие                                                                                              | Ожидаемый результат                                |
|-----|-------------------------------------------------------------------------------------------------------|----------------------------------------------------|
| 1   | 1С отправляет запрос POST /documents/outgoing с заголовком Authorization: Bearer invalid_token        | Сервер возвращает HTTP 401 Unauthorized            |
| 2   | Тело ответа содержит JSON с ошибкой: {"error": "unauthorized", "message": "Invalid or expired token"} | Доступ к ресурсу запрещён, документ не сохраняется |
| 3   | Повторить запрос без заголовка Authorization                                                          | Аналогично 401                                     |
|     |                                                                                                       |                         

**Дополнительно (позитивный контроль):**
С валидным токеном запрос проходит успешно (202 Accepted).

## TC-06: Битый (невалидный) XML от СБИС в webhook (400 Bad Request)

| Шаг | Действие                                                                                                                                                            | Ожидаемый результат                                                 |
|-----|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------|
| 1   | СБИС (или симулятор) отправляет на POST /webhooks/sbis/incoming тело, содержащее невалидный XML (например, незакрытый тег: <Документ><Идентификатор>123</Документ>) | Шлюз возвращает HTTP 400 Bad Request                                |
| 2   | Тело ответа содержит описание ошибки: {"error": "bad_request", "message": "XML parsing error: mismatched tag"}                                                      | Документ не сохраняется в БД, уведомление в очередь не отправляется |
| 3   | В логах шлюза фиксируется ошибка парсинга с указанием причины                                                                                                       | Администратор может диагностировать проблему                        |
|     |                                                                                                                                 

**Дополнительные варианты:**
- Пустое тело → 400
- XML с неверной кодировкой → 400
- XML, не соответствующий ожидаемой схеме (например, отсутствует обязательный тег Идентификатор) → 400 или 422 (Unprocessable Entity)

## TC-07: Дубликат документа (предотвращение повторной обработки)

| Шаг | Действие                                                                                                        | Ожидаемый результат                                                                                                                   |
|-----|-----------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| 1   | 1С отправляет документ с уникальным number и date (например, УПД-42 от 15.03.2025)                              | Шлюз принимает, возвращает 202 Accepted, документ сохраняется в БД со статусом pending                                                |
| 2   | 1С (случайно или из-за сбоя) повторно отправляет точно такой же документ (те же поля number, date, receiverInn) | Шлюз должен распознать дубликат (например, по хэшу или комбинации полей)                                                              |
| 3   | Шлюз возвращает ответ с HTTP кодом 409 Conflict                                                                 | Тело ответа: {"error": "duplicate", "message": "Document with same number and date already exists", "existingRequestId": "req_12345"} |
| 4   | Дубликат не ставится в очередь, в БД не добавляется новая запись                                                | Исходный документ не затрагивается                                                                                                    |
|     |                                                                                                                 |               

**Альтернативный сценарий (идемпотентность):**
Если система поддерживает идемпотентность по заголовку Idempotency-Key, при повторном запросе с тем же ключом следует вернуть тот же requestId и статус 202 без создания дубля. В данном тесте проверяется именно случай без явного ключа.

**Негативный подвариант:**
Если дубликат обнаружен на этапе, когда оригинал уже отправлен в СБИС, ответ может быть 200 OK с информацией о существующем документе, но без повторной отправки.
