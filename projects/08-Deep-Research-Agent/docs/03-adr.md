# Architecture Decision Records (ADR)

## 1. Назначение документа

Данный документ содержит журнал ключевых архитектурных решений, принятых в ходе разработки проекта **Deep Research Agent**. 

Формат ADR позволяет зафиксировать контекст, альтернативы и последствия каждого выбора. Это особенно важно для систем с использованием LLM, где поведение модели недетерминировано, а ограничения (контекст, галлюцинации) требуют специфических архитектурных обходных путей.

---

## ADR-001: Использование локальных LLM (Ollama) вместо облачных API

**Статус:** Принято.
**Контекст:** Для работы системы требуются две модели: одна для рассуждений (Planning/Synthesis), другая для вызова инструментов (Tool Calling). Использование OpenAI/Anthropic стоит денег и требует передачи данных в облако.

**Решение:** 
Развернуть локальный инференс-сервер **Ollama** на хост-машине с GPU (RTX 4060, 8GB VRAM). Использовать модели `deepseek-r1:8b` и `qwen2.5:7b`.

**Последствия:**
- ✅ **Плюсы:** Полностью бесплатное использование, конфиденциальность данных (запросы не уходят третьим лицам), отсутствие лимитов на количество токенов.
- ❌ **Минусы:** Привязка к железу (требуется GPU), скорость генерации ниже, чем у облачных флагманов (время ответа системы 30–60 секунд). Ограничение контекстного окна (у 7-8B моделей оно меньше, чем у GPT-4).

## ADR-002: Мультиагентная архитектура (Hub & Spoke) вместо одного агента

**Статус:** Принято.
**Контекст:** Изначально система проектировалась как один ИИ-агент, который получает запрос, сам ищет информацию и сам пишет ответ. Однако при тестировании выяснилось, что одна 7B-модель «задыхается» от объема задач: она забывала инструкции, путала форматы и выдавала нерелевантные ответы.

**Решение:** 
Разделить процесс на три специализированные роли (линейный пайплайн):
1. **Planner** (декомпозиция задачи на запросы).
2. **Researcher** (поиск и сбор сырых данных).
3. **Critic** (фильтрация, анализ и форматирование).

**Последствия:**
- ✅ **Плюсы:** Каждая модель получает узкую задачу и четкие инструкции. Значительно снизился уровень галлюцинаций. Появилась возможность использовать разные модели под разные задачи (Reasoning vs Tool Calling).
- ❌ **Минусы:** Увеличилось общее время ответа (три последовательных вызова LLM). Усложнилась передача данных между узлами (потребовалось явное указание переменных `$('NodeName')`).

## ADR-003: Использование Code Tool (JS) вместо HTTP Request Tool для SearXNG

**Статус:** Принято.
**Контекст:** Стандартный узел `HTTP Request Tool` в n8n отлично подходит для простых API, но он возвращает агенту **весь сырой JSON-ответ**. Поисковик SearXNG отдает массив с огромным количеством системного мусора (`img_src`, `parsed_url`, `template` и т.д.). Передача этого объема (10 000+ токенов) в 7B-модель приводила к переполнению контекста, зависаниям и галлюцинациям.

**Решение:** 
Написать кастомный инструмент на базе узла **Code Tool** (JavaScript). Код самостоятельно делает HTTP-запрос к SearXNG, извлекает только нужные поля (`title`, `url`, `snippet`) и обрезает текст до 400 символов, возвращая модели чистый массив данных.

**Последствия:**
- ✅ **Плюсы:** Размер контекста сократился в 5-6 раз. Модель перестала «сходить с ума» и начала четко следовать инструкциям. Появилась возможность обрабатывать ошибки сети (try/catch) и возвращать модели понятные тексты ошибок.
- ❌ **Минусы:** Потребовалось написание и поддержка JS-кода. Также пришлось использовать встроенный метод `this.helpers.httpRequest` вместо стандартного `fetch`, так как среда n8n изолирована.

## ADR-004: Передача исходного вопроса пользователя на этап «Критика»

**Статус:** Принято.
**Контекст:** Узел «Критик» изначально получал на вход только результаты поиска от «Исследователя». Из-за этого модель не понимала контекст исходного вопроса. Например, на запрос «найди минусы», она находила и плюсы, и минусы, и писала в ответе: *«Я предполагаю, что вы хотели узнать характеристики...»*. Это ломало UX.

**Решение:** 
В системный промпт узла «Критик» принудительно добавить передачу исходного текста сообщения пользователя напрямую из триггера: `{{ $('Telegram Trigger').first().json.message.text }}`.

**Последствия:**
- ✅ **Плюсы:** Критик всегда знает, на какой именно вопрос он отвечает, и фокусируется только на релевантных аспектах (например, только на минусах). Из ответов исчезли фразы «предположим» и «возможно».
- ❌ **Минусы:** Незначительное увеличение размера промпта (на длину исходного вопроса).

## ADR-005: Разделение моделей по ролям (Reasoning vs Instruct)

**Статус:** Принято.
**Контекст:** Модели с поддержкой Tool Calling (вызова инструментов) ведут себя по-разному. `deepseek-r1:8b` тратит много токенов на «размышления» (thinking) перед вызовом инструмента, что замедляет работу. `qwen2.5:7b` действует быстрее и точнее формирует JSON для вызова инструмента, но хуже справляется со сложной аналитикой.

**Решение:** 
Разделить зоны ответственности:
- `deepseek-r1:8b` (Reasoning) — используется для Планировщика и Критика, где нужно логическое мышление, анализ и синтез.
- `qwen2.5:7b` (Instruct/Tools) — используется для Researcher'а, где главное — быстро и точно вызвать инструмент и собрать данные.

**Последствия:**
- ✅ **Плюсы:** Максимальная эффективность каждой модели на своем участке. Система работает быстрее и точнее, чем если бы обе роли выполняла одна модель.
- ❌ **Минусы:** В оперативную память (VRAM) загружаются две разные модели (Ollama управляет этим автоматически, но переключение между ними может занимать несколько секунд).
