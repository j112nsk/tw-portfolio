# Architecture Decision Records (ADR)

## 1. Назначение документа

Данный документ содержит журнал ключевых архитектурных решений, принятых в ходе разработки проекта **Universal AI Assistant (Deep Research Agent)**. 

Формат ADR позволяет зафиксировать контекст, альтернативы и последствия каждого выбора. Это особенно важно для систем с использованием LLM, где поведение модели недетерминировано, а ограничения (контекст, галлюцинации) требуют специфических архитектурных обходных путей.

---

## ADR-001: Использование локальных LLM (Ollama) вместо облачных API

**Статус:** Принято.
**Контекст:** Для работы системы требуются модели для рассуждений (Planning/Synthesis) и для вызова инструментов (Tool Calling). Использование OpenAI/Anthropic стоит денег и требует передачи данных в облако.

**Решение:** 
Развернуть локальный инференс-сервер **Ollama** на хост-машине с GPU (RTX 4060, 8GB VRAM). Использовать модели `deepseek-r1:8b` и `qwen2.5:7b`.

**Последствия:**
- ✅ **Плюсы:** Полностью бесплатное использование, конфиденциальность данных (запросы не уходят третьим лицам), отсутствие лимитов на количество токенов.
- ❌ **Минусы:** Привязка к железу (требуется GPU), скорость генерации ниже, чем у облачных флагманов. Ограничение контекстного окна (у 7-8B моделей оно меньше, чем у GPT-4).

## ADR-002: Мультиагентная архитектура (Hub & Spoke) вместо одного агента

**Статус:** Принято.
**Контекст:** Изначально система проектировалась как один ИИ-агент, который получает запрос, сам ищет информацию и сам пишет ответ. Однако при тестировании выяснилось, что одна 7B-модель «задыхается» от объема задач: она забывала инструкции, путала форматы и выдавала нерелевантные ответы.

**Решение:** 
Разделить процесс на три специализированные роли (линейный пайплайн для ветки поиска):
1. **Planner** (декомпозиция задачи на запросы).
2. **Researcher** (поиск и сбор сырых данных).
3. **Critic** (фильтрация, анализ и форматирование).

**Последствия:**
- ✅ **Плюсы:** Каждая модель получает узкую задачу и четкие инструкции. Значительно снизился уровень галлюцинаций. Появилась возможность использовать разные модели под разные задачи.
- ❌ **Минусы:** Увеличилось общее время ответа для сложных запросов (три последовательных вызова LLM). Усложнилась передача данных между узлами.

## ADR-003: Использование Code Tool (JS) вместо HTTP Request Tool для SearXNG

**Статус:** Принято.
**Контекст:** Стандартный узел `HTTP Request Tool` в n8n возвращает агенту **весь сырой JSON-ответ**. Поисковик SearXNG отдает массив с огромным количеством системного мусора (10 000+ токенов). Передача этого объема в 7B-модель приводила к переполнению контекста и галлюцинациям.

**Решение:** 
Написать кастомный инструмент на базе узла **Code Tool** (JavaScript). Код самостоятельно делает HTTP-запрос, извлекает только нужные поля (`title`, `url`, `snippet`) и обрезает текст до 400 символов.

**Последствия:**
- ✅ **Плюсы:** Размер контекста сократился в 5-6 раз. Модель перестала «сходить с ума». Появилась возможность обрабатывать ошибки сети (try/catch).
- ❌ **Минусы:** Потребовалось написание и поддержка JS-кода (использование `this.helpers.httpRequest` вместо `fetch`).

## ADR-004: Передача исходного вопроса пользователя на этап «Критика»

**Статус:** Принято.
**Контекст:** Узел «Критик» изначально получал на вход только результаты поиска. Из-за этого модель не понимала контекст исходного вопроса. Например, на запрос «найди минусы», она находила и плюсы, и минусы, и писала: *«Я предполагаю, что вы хотели узнать характеристики...»*.

**Решение:** 
В системный промпт узла «Критик» принудительно добавить передачу исходного текста сообщения пользователя напрямую из триггера: `{{ $('Telegram Trigger').first().json.message.text }}`.

**Последствия:**
- ✅ **Плюсы:** Критик всегда знает, на какой именно вопрос он отвечает, и фокусируется только на релевантных аспектах. Из ответов исчезли фразы «предположим».
- ❌ **Минусы:** Незначительное увеличение размера промпта.

## ADR-005: Разделение моделей по ролям (Reasoning vs Instruct)

**Статус:** Принято.
**Контекст:** Модели с поддержкой Tool Calling ведут себя по-разному. `deepseek-r1:8b` тратит много токенов на «размышления» перед вызовом инструмента, что замедляет работу. `qwen2.5:7b` действует быстрее, но хуже справляется со сложной аналитикой.

**Решение:** 
Разделить зоны ответственности:
- `deepseek-r1:8b` — Планировщик, Критик, Direct Agent (где нужно логическое мышление и генерация текста).
- `qwen2.5:7b` — Researcher и Router (где главное — быстро обработать запрос и вызвать инструмент).

**Последствия:**
- ✅ **Плюсы:** Максимальная эффективность каждой модели на своем участке. Система работает быстрее и точнее.
- ❌ **Минусы:** В VRAM загружаются две разные модели (Ollama управляет этим автоматически, но переключение занимает время).

## ADR-006: Внедрение паттерна Router (Маршрутизация запросов)

**Статус:** Принято.
**Контекст:** Изначально система была заточена только под поиск (Deep Research). При запросах вроде «напиши код» или «переведи текст» система всё равно шла в SearXNG. Это приводило к перерасходу ресурсов GPU (3 вызова LLM + парсинг) и замедляло ответ в 10 раз, хотя ответ был известен модели изначально.

**Решение:** 
Внедрить узел-классификатор `Router` сразу после триггера. Он определяет намерение пользователя (Intent) и через узел `Switch` направляет запрос в одну из двух веток:
1. **DIRECT:** Прямой ответ легковесной моделью без поиска (для кода, общих знаний, переводов).
2. **RESEARCH:** Запуск полного пайплайна (Планировщик -> Агент -> Критик).

**Последствия:**
- ✅ **Плюсы:** Скорость ответа на простые запросы упала с 40 секунд до 5-10. Экономия ресурсов GPU. Система стала «универсальным ассистентом», а не просто «поисковиком».
- ❌ **Минусы:** Добавился один дополнительный вызов LLM (Router) в начало пайплайна (около 1-2 секунд задержки).

## ADR-007: Использование AI Agent вместо Basic LLM Chain для Direct-ветки

**Статус:** Принято.
**Контекст:** Для ветки DIRECT изначально использовался узел `Basic LLM Chain`. Однако в n8n узлы типа `Chain` **технически не поддерживают** подключение узлов памяти (Memory). Из-за этого бот забывал контекст диалога (например, имя пользователя), если запрос уходил в ветку DIRECT.

**Решение:** 
Заменить `Basic LLM Chain` на узел `AI Agent`. Оставить слот `Tool` пустым (чтобы агент не пытался искать в интернете) и подключить к нему `Simple Memory` с ключом сессии по `chat.id`.

**Последствия:**
- ✅ **Плюсы:** Ассистент помнит контекст диалога в обеих ветках. Унифицирована структура управления моделями.
- ❌ **Минусы:** Узел `AI Agent` требует чуть больше оперативной памяти при инициализации, чем простой `Chain`.

## ADR-008: Универсальное выражение для отправки сообщений в Telegram

**Статус:** Принято.
**Контекст:** После внедрения Router у нас появилось две ветки (RESEARCH и DIRECT), которые сходятся в один узел отправки `Send a text message`. Однако узлы `AI Agent` возвращают текст в поле `output`, а узлы `Basic LLM Chain` (Критик) — в поле `text`. Из-за этого Telegram выдавал ошибку `Bad Request: message text is empty` при попытке отправить ответ из одной из веток.

**Решение:** 
В узле `Send a text message` в поле `Text` использовать логическое ИЛИ: `{{ $json.output || $json.text }}`. Этот код берет текст из поля `output`, а если его нет — из поля `text`.

**Последствия:**
- ✅ **Плюсы:** Единая точка отправки сообщений для любых типов узлов. Код устойчив к изменениям структуры выходных данных.
- ❌ **Минусы:** Незначительное усложнение выражения в узле (с точки зрения читаемости для новичков).

## ADR-009: Использование нативного узла Telegram вместо HTTP Request для Send Chat Action

**Статус:** Принято.
**Контекст:** Для реализации статуса «печатает...» изначально использовался узел `HTTP Request`, который делал прямой запрос к Telegram Bot API. Токен бота приходилось прописывать в URL (или использовать переменные окружения), что создавало риск его случайной утечки при экспорте воркфлоу в Git, а также усложняло конфигурацию.

**Решение:** 
Заменить узел `HTTP Request` на нативный узел `Telegram` (Resource: `Message`, Operation: `Send Chat Action`). Этот узел берет токен напрямую из Credentials, которые n8n никогда не экспортирует в JSON-файл.

**Последствия:**
- ✅ **Плюсы:** Безопасность (токен надежно скрыт). Простота настройки. Уменьшение количества узлов в воркфлоу. Отпадает необходимость использовать `.env` файлы и переменные `$env`.
- ❌ **Минусы:** Отсутствуют.
