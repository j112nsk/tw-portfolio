## 1. Контекст

В модели v2.x тестовое задание — отдельная сущность (`test_assignments`), не являющаяся этапом. У неё свои поля: дата получения, срок сдачи, дата сдачи, комментарий о результате. Тестовое участвует в правилах SR7 (учёт события), SR9 (причина отказа) и SR13 (напоминание о сроке сдачи).

Опыт личной эксплуатации (октябрь 2026) показал:

1. Большинство тестовых заданий фиксируется простой записью: «получено», «срок», «сдано». Структура из четырёх полей избыточна.
2. Форма требует двойной работы: сначала зафиксировать факт выдачи тестового, потом — что оно сдано; при этом в истории этапов тестовое не отражается.
3. SQL-запросы и тесты усложняются проверками «есть ли тестовое» в нескольких местах (SR9, SR13, Q1, US-12).

## 2. Решение

**Тестовое задание становится обычным этапом отбора.**

- Добавляется статус `TEST_ASSIGNMENT` («Тестовое задание»): `kind = 'stage'`, `is_required_stage = false`, `in_funnel = false`.
- Порядок этапа (`stage_order`): между «HR-интервью» и «Техническое собеседование» (после HR, до Тех). Порядок определяет типичную последовательность, но не жёсткое ограничение: пользователь может установить тестовое в любом месте до «Знакомства», при отклонении от канонического порядка — предупреждение о нетипичном переходе (D14, SR2).
- Таблица `test_assignments`, связанные функции, правила INV-13 и INV-20 удаляются.
- Срок сдачи и результат сдачи записываются **текстом в комментарии** к записи истории. Формат свободный: «срок 25.10, сдано 24.10» или «сдал, ждём ответа».
- Несколько тестовых на одном процессе допускаются: этап `TEST_ASSIGNMENT` можно установить повторно (как любое повторное прохождение, SR12).

**Отменяются:**

- Статус `APPLIED` («Отклик»). Он был нужен только для случая «первым выдано тестовое» (D25). Теперь в этой ситуации пользователь ставит `TEST_ASSIGNMENT` первой записью.
- Правило SR7 в прежнем виде (тестовое как событие) — переписывается.
- Строка «только тестовое» в воронке (US-12, критерий 5).
- Напоминание о сроке сдачи тестового (SR13). Напоминаются только сами этапы.
- Правила INV-13 (срок/сдача не раньше получения) и INV-20 (процесс, начатый с «Отклика», имеет тестовое).

**Меняется:**

- SR9 (причина отказа): причина обязательна, если в истории есть `HR_INTERVIEW` **или** `TEST_ASSIGNMENT`.
- D25 (начальный статус): начальный статус процесса — любой этап; отдельного «Отклика» нет.

## 3. Последствия

**Что выигрываем:**

- Один механизм для всех этапов отбора: меньше таблиц, меньше кода, меньше проверок.
- Срок сдачи и результат — в свободной форме, без строгих полей.
- История становится единственным источником истины: любые правки — через правку записи истории.
- Упрощение SQL (Q1, Q4) и упрощение SR9, SR13.

**Что теряем:**

- Нет структурированных полей «срок сдачи» и «сдано/не сдано». Напоминаний о сроке тестового больше не будет — пользователь смотрит в комментарий.
- Отчёт «сколько тестовых сдано в срок / просрочено» автоматически не построить.
- При миграции: удаляется `test_assignments`; процессы с единственной записью `APPLIED` удаляются; из остальных удаляются записи `APPLIED`. Демонстрационные данные перегенерируются; существующие процессы в рабочей базе пользователя переделываются вручную (1–2 штуки).

**Ограничения:**

- В аналитике тестовое не участвует (не в воронке), но видно в истории и в общем числе процессов.
- Функция «редактировать запись истории» (новинка этой же итерации) позволяет менять **дату, комментарий, статус и причину отказа**. При смене статуса на нетипичный переход (D14, SR2) — предупреждение и подтверждение, как в форме «Назначить этап». Текущий статус процесса пересчитывает триггер `process_status_history_sync_status` по последней записи (`recorded_at`, затем `id`), потому что после правки не-последней записи текущий статус может не измениться.
- Отдельной формы «Переименовать статус записи» нет: одна форма покрывает все правки истории. Записи истории остаются неизменяемыми по `recorded_at` и `id` — это сохраняет порядок сортировки (свежие сверху), даже если дата этапа в правке меняется.

## 4. Альтернативы

**A. Оставить `test_assignments` как отдельную сущность.** Отклонено: опыт эксплуатации показал, что структура избыточна, а двойная форма утомляет.

**B. Сохранить оба способа.** `test_assignments` для структурированных данных, плюс `TEST_ASSIGNMENT` как этап. Отклонено: два способа вести одно и то же — источник путаницы и расхождений.

**C. Расширить `test_assignments` (различать «получено», «сдано», «результат» отдельными полями).** Отклонено: углубляет проблему вместо её решения.

## 5. Связанные решения

| ID | Что меняется |
|----|--------------|
| D9 (воронка) | Добавляется необязательный этап «Тестовое задание» между «Техническим собеседованием» и «Знакомством с командой»; в воронке не участвует |
| D21 (даты) | Без изменений; тестовое — обычная запись истории с датой |
| D25 (начальный статус) | Отменяется. Начальный статус — любой этап. Отдельного «Отклика» нет |
| SR7 (тестовое) | Переписывается: тестовое = этап |
| SR9 (причина отказа) | Причина обязательна, если в истории есть HR-интервью или Тестовое задание |
| SR13 (напоминания) | Упрощается: только этапы; срок сдачи тестового не напоминается |
| INV-13, INV-20 | Отменяются |
| Q1 (воронка) | Без строки «только тестовое» |
| Q4 (напоминания) | Без срока сдачи тестового |
| US-07 (тестовое задание) | Отменяется как отдельная история |
