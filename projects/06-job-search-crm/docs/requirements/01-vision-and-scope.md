## 1. Контекст и проблема

Поиск работы ведётся одновременно по двум направлениям:

- **Системный / бизнес-аналитик (SA/BA);**
- **Технический писатель (TW).**

У каждого направления своё резюме, свои ключевые слова поиска и свои требования к
навыкам. Основной канал поиска и откликов: hh.ru. Дополнительно используются два
тематических Telegram-канала (по одному на направление), где размещены резюме и иногда
публикуются вакансии; отклики также уходят по почте, если вакансия найдена на сайте
компании. Иногда работодатель выходит на соискателя первым.

Объём поиска: около 50 откликов в неделю по SA/BA и около 20 по TW. Сейчас отклики
нигде не фиксируются.

Из-за этого возникают четыре проблемы:

- **Теряется контроль:** при таком объёме невозможно помнить, на какой стадии каждый
  отклик, где ждать ответа, какие процессы пора закрыть как «Нет ответа».
- **Два потока смешиваются:** общая статистика не показывает, какое направление
  работает лучше.
- **Нет обратной связи по процессу:** нельзя измерить, какие источники вакансий и
  каналы отклика дают приглашения на интервью.
- **Решения принимаются интуитивно:** нет данных о том, каких навыков не хватает
  относительно требований работодателей по каждому направлению и какие зарплатные
  вилки реалистичны.

## 2. Видение

Простое локальное приложение, в котором соискатель в одном месте ведёт отклики и
историю процессов по нескольким направлениям поиска, тратя на ввод не более минуты
на отклик, а по накопленным данным получает ответы на вопросы: что работает в моём
поиске, какое направление, источник и канал отклика результативнее, что мне стоит
подтянуть и куда направить усилия.

Проект одновременно служит портфолио-кейсом по обоим направлениям:

- для **SA/BA**: полный цикл аналитических артефактов от требований до работающего
  прототипа;
- для **TW**: пакет пользовательской и технической документации к продукту,
  оформленный по единому стилю.

## 3. Цели

| ID | Цель | Измеримый критерий успеха |
|----|------|---------------------------|

## 6. Границы проекта (Scope)

### 6.1. Входит в проект

- Ручной ввод откликов (данные берутся человеком с job-сайтов, без автоматического сбора);
  форма быстрого ввода с подстановкой значений из предыдущего отклика.
- Учёт только тех вакансий, по которым принято решение откликнуться или согласиться на
  общение с работодателем, который вышел на соискателя первым.
- Справочник направлений поиска; каждая вакансия относится к одному направлению.
- Раздельный учёт источника вакансии (где найдена), канала отклика (как откликнулся или
  как связался работодатель), инициатора процесса (соискатель или работодатель) и
  признака сопроводительного письма.
- Воронка этапов и история событий по каждому процессу (смена этапа, дата, комментарий).
- Тестовые задания как события внутри любого этапа (получено, срок сдачи, сдано, результат).
- Учёт контактов (рекрутёры, нанимающие менеджеры) в минимальном объёме.
- Список «требуют действия»: процессы к закрытию как «Нет ответа», просроченная
  договорённая обратная связь, интервью и сроки тестовых заданий в ближайшие 7 дней.
- Массовое подтверждение закрытия процессов как «Нет ответа».
- Ввод навыков вручную для вакансий, дошедших до интервью; профиль навыков соискателя
  отдельно для каждого направления.
- Зарплатная вилка в рублях как необязательное поле.
- Дашборд и набор аналитических SQL-запросов (ответы на Q1–Q11).
- Демонстрационные синтетические данные для публичного репозитория.
- Комплект аналитической документации: требования, процессы, модель данных, ADR, тест-кейсы.
- Комплект пользовательской и технической документации: руководство пользователя,
  быстрый старт, FAQ, глоссарий, стайлгайд, журнал изменений.

### 6.2. Не входит в проект

| Что исключено | Почему |
|---------------|--------|
| Автоматический сбор вакансий (API, скрапинг hh.ru и других площадок) | Публичный API закрыт, скрапинг нарушает правила площадок и нестабилен. Решение фиксируется в ADR |
| Многопользовательский режим, авторизация, роли | Система личная, один пользователь |
| Облачный деплой и продакшен-безопасность | Достаточно локального запуска; вопросы безопасности описываются в рисках |
| Автоматическая отправка откликов и писем | Выходит за рамки учёта и аналитики |
| Интеграция с почтой и календарём | Усложняет MVP, можно добавить позже |
| Хранение файлов и текстов (резюме, сопроводительные письма, тексты вакансий) | Не нужно для аналитики воронки |
| Версии резюме | Решение автора (D2): по одному резюме на направление, версии не предполагаются |
| Проверка статистической значимости (A/B-тесты) | Выборка слишком мала; показываем только описательную статистику и размер выборки |
| Автоматическая классификация вакансий по направлениям | Направление выбирает человек при вводе |
| Учёт вакансий, на которые решено не откликаться, и причин отказа от отклика | Решение автора (D5): в системе фиксируются только вакансии, по которым принято решение откликаться |
| Мультивалютность | Решение автора (D6): все зарплатные вилки хранятся в рублях |
| Автоматическое извлечение навыков из текста вакансии | Решение автора (D8): навыки вводятся вручную для вакансий, дошедших до интервью; возможное развитие после MVP |
| Автоматическое закрытие откликов | Решение автора (D10): система только предлагает список к закрытию, подтверждает человек |
| Восстановление истории поиска до запуска системы | Ранее отклики не фиксировались; при запуске переносятся только активные процессы |
| Мобильное приложение, push-уведомления | Достаточно веб-интерфейса на компьютере |

## 7. Ограничения

- Только бесплатные инструменты.
- Платформа разработки: Windows 11.
- Стек: PostgreSQL, Python, Streamlit, Git.
- Язык документации: русский; имена объектов БД и кода: английские.
- Персональные данные (реальные компании, контакты, переписка) хранятся только
  локально и не попадают в публичный репозиторий.
- Работа ведётся в свободное время, ориентир по срокам: 3–4 недели. Приоритет первого
  этапа: минимальный MVP (быстрый ввод откликов и смена этапов).

## 8. Допущения

- Объём ввода: около 70 откликов в неделю (около 50 по SA/BA и около 20 по TW), то есть
  примерно 300 в месяц и 3–4 тысячи в год.
- Отклик вносится в систему в день отправки.
- Рабочие дни: понедельник–пятница, государственные праздники не учитываются.
- Работа в системе ведётся с одного компьютера.
- Объём данных (тысячи записей в год) не создаёт проблем производительности для СУБД.
- Большая часть откликов закрывается без ответа, поэтому массовое закрытие процессов
  является штатной операцией.

## 9. Первичные риски

| ID | Риск | Вероятность | Влияние | Меры |
|----|------|-------------|---------|------|
| R1 | Ручной ввод 70 откликов в неделю утомляет, и систему перестают вести | Высокая | Высокое | Форма быстрого ввода: 4 обязательных поля, остальное подставляется из предыдущего отклика; ввод с клавиатуры; массовое закрытие «Нет ответа» |
| R2 | Малая выборка, разделённая на два направления, приводит к ложным выводам; особенно мала выборка вакансий, дошедших до интервью | Высокая | Среднее | Явно показывать размер выборки на дашборде и в рейтинге навыков; описать ограничения в документации |
| R3 | Утечка персональных данных в публичный репозиторий | Средняя | Высокое | Вложенный `.gitignore`, синтетические демо-данные, проверка `git status` перед коммитом |
| R4 | Расползание объёма (scope creep) | Высокая | Среднее | Явный список «не входит»; новые идеи фиксируются в бэклоге, а не реализуются сразу |
| R5 | Площадка меняет правила, использование данных становится спорным | Низкая | Среднее | Данные с площадок только для личного использования, в репозиторий не публикуются |
| R6 | Объём документации вытесняет работающий прототип (или наоборот) | Средняя | Среднее | Сначала MVP и минимальный комплект документов, затем расширение; контрольные точки по этапам |
| R7 | Два направления усложняют модель и интерфейс | Средняя | Среднее | Направление реализуется как справочник и сквозной фильтр, а не как два отдельных контура |
| R8 | Смещение выборки: в системе только вакансии с откликом, а навыки проставляются только для вакансий, дошедших до интервью, поэтому аналитика навыков и вилок отражает требования работодателей, которые пригласили соискателя, а не весь рынок | Высокая | Среднее | Указывать на дашборде, по какой выборке построен показатель; описать ограничение в документации по аналитике |
| R9 | Пока система не запущена, отклики не фиксируются (до 70 в неделю), и данные для аналитики накапливаются медленнее | Высокая | Среднее | Первым этапом выпускается минимальный MVP (быстрый ввод и смена этапов); навыки, аналитика и документация добавляются позже |

## 10. Принятые решения

| ID | Решение |
|----|---------|
| D1 | Направление поиска хранится в справочнике (сейчас два значения: SA/BA и TW). Каждая вакансия относится ровно к одному направлению |
| D2 | Для каждого направления ведётся одно резюме, версии не предполагаются. Отдельная сущность «версия резюме» не создаётся: резюме однозначно определяется направлением вакансии |
| D3 | Профиль навыков соискателя ведётся отдельно для каждого направления |
| D4 | Документация ведётся на русском, имена в БД и коде на английском |
| D5 | В системе хранятся только вакансии, по которым принято решение откликаться (закрывает OQ2). Следствие: аналитика строится по вакансиям с откликом, ограничение указывается на дашборде |
| D6 | Все зарплатные вилки хранятся в рублях, мультивалютность не поддерживается (закрывает OQ3) |
| D7 | Направление вакансии определяется резюме, с которым соискатель откликается. Гибридные вакансии СА/БА/Fullstack относятся к SA/BA; пересечений между SA/BA и TW нет (закрывает OQ4) |
| D8 | Навыки проставляются вручную только для вакансий, дошедших до интервью; для остальных откликов не вводятся. Тексты вакансий не хранятся. Следствие: Q5 и Q6 строятся только по таким вакансиям |
| D9 | Основная воронка одинакова для обоих направлений: Отклик → HR-интервью → Техническое собеседование → Знакомство с командой (необязательный этап) → СБ (необязательный этап) → Оффер. Тестовое задание не является этапом, а событием на любом этапе. Итоги процесса: оффер принят, оффер отклонён мной, отказ работодателя, мой отказ, нет ответа. Допустимые переходы описываются в статусной модели |
| D10 | Процесс становится кандидатом на закрытие как «Нет ответа» через 10 рабочих дней после даты отклика (пн–пт, без учёта праздников). Система не закрывает отклики сама, а показывает список к закрытию, который подтверждается человеком, в том числе массово. Договорённая дата обратной связи хранится в процессе и используется в списке «требуют действия» |
| D11 | Процессы, начатые работодателем (HR вышел на соискателя первым), фиксируются в системе только если соискатель согласился на общение. Они помечаются инициатором «работодатель» и не участвуют в расчёте конверсии «отклик → ответ» |
| D12 | Источник вакансии (где найдена) и канал отклика (hh.ru, Telegram, почта, ответ на входящее сообщение) хранятся раздельно. Для отклика хранится признак сопроводительного письма; значения по умолчанию берутся из предыдущего отклика |

## 11. Открытые вопросы

| ID | Вопрос | Предварительный ответ |
|----|--------|-----------------------|
| OQ5 | Как считать «Нет ответа», если ответ был, а затем наступила тишина? | Если после ответа 10 рабочих дней нет событий и нет договорённой даты, процесс попадает в список к закрытию с итогом «Нет ответа» |
| OQ6 | Считается ли HR-интервью «интервью» для условия D8 (ввод навыков)? | Да: навыки вводятся для откликов, дошедших до HR-интервью или дальше |
