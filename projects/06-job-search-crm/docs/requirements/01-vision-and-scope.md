## 1. Контекст и проблема

Поиск работы ведётся одновременно по двум направлениям:

- **Системный / бизнес-аналитик (SA/BA);**
- **Технический писатель (TW).**

У каждого направления своё резюме, свои ключевые слова поиска и свои требования к
навыкам. Вакансии приходят из нескольких каналов: job-сайты, Telegram-каналы,
рекомендации знакомых. Информация о вакансиях, откликах и общении с рекрутёрами
разбросана по закладкам, заметкам и перепискам.

Из-за этого возникают четыре проблемы:

- **Теряется контроль:** непонятно, на какой стадии каждый отклик, где пора
  написать follow-up, где вообще не было ответа.
- **Два потока смешиваются:** общая статистика не показывает, какое направление
  и какая версия резюме работают лучше.
- **Нет обратной связи по процессу:** нельзя измерить, какие источники дают
  приглашения на интервью.
- **Решения принимаются интуитивно:** нет данных о том, каких навыков не хватает
  относительно требований рынка по каждому направлению и какие зарплатные вилки
  реалистичны.

## 2. Видение

Простое локальное приложение, в котором соискатель в одном месте ведёт вакансии,
отклики и историю общения по нескольким направлениям поиска, а по накопленным
данным получает ответы на вопросы: что работает в моём поиске, какое направление и
какая версия резюме результативнее, что мне стоит подтянуть и куда направить усилия.

Проект одновременно служит портфолио-кейсом по обоим направлениям:

- для **SA/BA**: полный цикл аналитических артефактов от требований до работающего
  прототипа;
- для **TW**: пакет пользовательской и технической документации к продукту,
  оформленный по единому стилю.

## 3. Цели

| ID | Цель | Измеримый критерий успеха |
|----|------|---------------------------|
| G1 | Единый учёт вакансий, откликов и событий по ним | Все отклики за период поиска ведутся в системе; ни один не живёт только в заметках |
| G2 | Прозрачность воронки поиска отдельно по каждому направлению и версии резюме | Дашборд показывает конверсию между этапами и среднее время на этапе с фильтром по направлению и версии резюме без ручных расчётов |
| G3 | Понимание требований рынка и пробелов в навыках по каждому направлению | В базе не менее 50 вакансий, из них не менее 20 по каждому направлению; есть рейтинг востребованных навыков и сравнение с профилем навыков направления |
| G4 | Минимальные трудозатраты на ведение | Добавление вакансии занимает не более 2 минут |
| G5 | Демонстрация навыков системного / бизнес-аналитика | Опубликован комплект аналитических артефактов; прослеживается связь «цель → вопрос → требование → таблица → запрос» |
| G6 | Демонстрация навыков технического писателя | Опубликован пакет документации (руководство пользователя, быстрый старт, FAQ, глоссарий, стайлгайд, журнал изменений); по README и быстрому старту проект запускается за 30 минут на чистой Windows-машине |

## 4. Пользователи и заинтересованные стороны

| Роль | Описание | Интерес |
|------|----------|---------|
| Соискатель (основной пользователь) | Единственный пользователь системы, ведёт поиск по двум направлениям | Контроль процесса, аналитика, экономия времени |
| Читатель портфолио, направление SA/BA | Нанимающий менеджер или аналитик; не работает с системой | Оценить качество требований, моделей, SQL и трассируемости |
| Читатель портфолио, направление TW | Нанимающий менеджер или технический писатель; не работает с системой | Оценить структуру, ясность, единообразие и полноту документации |

## 5. Бизнес-вопросы, на которые должна отвечать система

Эти вопросы определяют, какие данные нужно хранить. Если данные для ответа на
вопрос не собираются, вопрос либо снимается, либо меняется модель данных.
Все вопросы, кроме Q4 и Q8, считаются в разрезе направлений поиска.

| ID | Вопрос | Связь с целью |
|----|--------|---------------|
| Q1 | Сколько откликов на каждом этапе воронки и какова конверсия между этапами? | G2 |
| Q2 | Сколько в среднем проходит дней от отклика до первого ответа и до интервью? | G2 |
| Q3 | Какие источники вакансий дают больше всего приглашений на интервью? | G2 |
| Q4 | По каким откликам давно нет движения и пора написать follow-up? | G1 |
| Q5 | Какие навыки чаще всего встречаются в вакансиях? | G3 |
| Q6 | Каких востребованных навыков нет в профиле навыков направления? | G3 |
| Q7 | Какие зарплатные вилки встречаются по типам компаний и форматам работы? | G3 |
| Q8 | По каким причинам я отказывался или мне отказывали? | G2 |
| Q9 | Какая версия резюме даёт больше ответов и приглашений на интервью? | G2 |
| Q10 | Как соотносятся затраченные усилия (число откликов) и результат (интервью, офферы) по направлениям? | G2 |

## 6. Границы проекта (Scope)

### 6.1. Входит в проект

- Ручной ввод вакансий (данные берутся человеком с job-сайтов, без автоматического сбора).
- Справочник направлений поиска; каждая вакансия относится к одному направлению.
- Учёт версий резюме (метаданные: название, направление, дата, заметка об изменениях).
- Учёт откликов и истории событий по каждому отклику (смена статуса, дата, комментарий).
- Учёт контактов (рекрутёры, нанимающие менеджеры) в минимальном объёме.
- Список «требуют действия»: отклики, по которым пора сделать follow-up.
- Теги навыков у вакансий и профиль навыков соискателя отдельно для каждого направления.
- Дашборд и набор аналитических SQL-запросов (ответы на Q1–Q10).
- Демонстрационные синтетические данные для публичного репозитория.
- Комплект аналитической документации: требования, процессы, модель данных, ADR, тест-кейсы.
- Комплект пользовательской и технической документации: руководство пользователя,
  быстрый старт, FAQ, глоссарий, стайлгайд, журнал изменений.

### 6.2. Не входит в проект

| Что исключено | Почему |
|---------------|--------|
| Автоматический сбор вакансий (API, скрапинг hh.ru и других площадок) | Публичный API закрыт, скрапинг нарушает правила площадок и нестабилен. Решение фиксируется в ADR |
| Многопользовательский режим, авторизация, роли | Система личная, один пользователь |
| Облачный деплой и продакшен-безопасность | Достаточно локального запуска; вопросы безопасности описываются в рисках |
| Автоматическая отправка откликов и писем | Выходит за рамки учёта и аналитики |
| Интеграция с почтой и календарём | Усложняет MVP, можно добавить позже |
| Хранение файлов (резюме, сопроводительные письма) | Не нужно для аналитики воронки; хранятся только метаданные версий резюме |
| Проверка статистической значимости (A/B-тесты) | Выборка слишком мала; показываем только описательную статистику и размер выборки |
| Автоматическая классификация вакансий по направлениям | Направление выбирает человек при вводе |
| Мобильное приложение, push-уведомления | Достаточно веб-интерфейса на компьютере |

## 7. Ограничения

- Только бесплатные инструменты.
- Платформа разработки: Windows 11.
- Стек: PostgreSQL, Python, Streamlit, Git.
- Язык документации: русский; имена объектов БД и кода: английские.
- Персональные данные (реальные компании, контакты, переписка) хранятся только
  локально и не попадают в публичный репозиторий.
- Работа ведётся в свободное время, ориентир по срокам: 3–4 недели.

## 8. Допущения

- Автору достаточно ручного ввода 20–50 вакансий в неделю суммарно по обоим направлениям.
- Работа в системе ведётся с одного компьютера.
- Данных для аналитики будет мало (десятки, максимум сотни записей), поэтому
  производительность СУБД не является критичной.

## 9. Первичные риски

| ID | Риск | Вероятность | Влияние | Меры |
|----|------|-------------|---------|------|
| R1 | Ручной ввод утомляет, и систему перестают вести | Средняя | Высокое | Минимальная форма ввода: обязательны только 4–5 полей; направление по умолчанию подставляется автоматически |
| R2 | Малая выборка, разделённая на два направления, приводит к ложным выводам | Высокая | Среднее | Явно показывать размер выборки на дашборде; описать ограничения в документации |
| R3 | Утечка персональных данных в публичный репозиторий | Средняя | Высокое | Вложенный `.gitignore`, синтетические демо-данные, проверка `git status` перед коммитом |
| R4 | Расползание объёма (scope creep) | Высокая | Среднее | Явный список «не входит»; новые идеи фиксируются в бэклоге, а не реализуются сразу |
| R5 | Площадка меняет правила, использование данных становится спорным | Низкая | Среднее | Данные с площадок только для личного использования, в репозиторий не публикуются |
| R6 | Объём документации вытесняет работающий прототип (или наоборот) | Средняя | Среднее | Сначала MVP и минимальный комплект документов, затем расширение; контрольные точки по этапам |
| R7 | Два направления усложняют модель и интерфейс | Средняя | Среднее | Направление реализуется как справочник и сквозной фильтр, а не как два отдельных контура |

## 10. Принятые решения

| ID | Решение |
|----|---------|
| D1 | Направление поиска хранится в справочнике (сейчас два значения: SA/BA и TW). Каждая вакансия относится ровно к одному направлению |
| D2 | Версия резюме принадлежит одному направлению. Отклик ссылается на конкретную версию резюме. Бизнес-правило: направление версии резюме должно совпадать с направлением вакансии |
| D3 | Профиль навыков соискателя ведётся отдельно для каждого направления |
| D4 | Документация ведётся на русском, имена в БД и коде на английском |
