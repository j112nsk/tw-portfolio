## 1. Назначение документа

Описать, как логическая модель реализована в PostgreSQL: типы данных, ограничения, триггеры,
индексы и порядок применения миграций. Документ содержит словарь данных и таблицу соответствия
правил целостности (INV-01–INV-18) их реализации.

## 2. Среда и соглашения

- **СУБД:** PostgreSQL. DDL написан для версии 14 и новее; конкретная версия фиксируется при
  установке (PM-01). До прогона на живой СУБД миграции считаются непроверенными.
- **База данных:** `job_search_crm`, кодировка UTF8, схема `public` (PQ1).
- **Имена:** таблицы и поля в `snake_case` на английском; первичный ключ всегда `id`
  (у связей — составной); внешний ключ называется `<сущность>_id`.
- **Имена ограничений:** `<таблица>_<суть>_chk` (проверка), `<таблица>_<суть>_uk` (уникальность).
  Внешние ключи получают имена PostgreSQL по умолчанию (`<таблица>_<поле>_fkey`).
- **Прочие объекты:** индексы `ix_<таблица>_<суть>`, функции триггеров `fn_<таблица>_<суть>`,
  триггеры `<таблица>_<суть>`.
- **Значения справочников** приложение и запросы выбирают по полю `code`, а не по числовому
  `id` (PM-03).

## 3. Типы данных

| Логический тип | Физический тип | Обоснование |
|----------------|----------------|-------------|
| Идентификатор справочника | `smallint generated always as identity` | Справочники малы; значения формирует СУБД |
| Идентификатор рабочих записей | `bigint generated always as identity` | Стандартный запас; ручная подстановка `id` запрещена |
| Идентификатор навыка | `integer generated always as identity` | Навыков может быть сотни |
| Текст | `text` | В PostgreSQL `varchar(n)` не даёт преимуществ; длины бизнес-правилами не заданы |
| Дата этапа или события | `date` | Время не хранится (D21) |
| Момент записи | `timestamptz` | Однозначный момент независимо от часового пояса (NFR-06) |
| Флаг | `boolean` | — |
| Деньги | `integer` | Целые рубли «на руки» (D15) |
| Инициатор, автор записи, тип статуса | `text` + `check` | Фиксированный набор значений, от которого зависят правила; в справочник не выносится (раздел 2 логической модели) |

## 4. Словарь данных

### 4.1. Простые справочники

Одинаковую структуру имеют `directions`, `vacancy_sources`, `employer_types`,
`employment_formats`, `rejection_reasons`.

| Поле | Тип | NULL | Ограничения | Назначение |
|------|-----|------|-------------|------------|
| `id` | smallint, identity | нет | PK | Идентификатор |
| `code` | text | нет | Уникален; формат `^[A-Z][A-Z0-9_]*$` | Стабильный код для приложения и запросов |
| `name_ru` | text | нет | Не пустой | Название в интерфейсе |
| `sort_order` | smallint | нет | — | Порядок вывода |

### 4.2. `channels` — каналы отклика и общения

Поля `id`, `code`, `name_ru`, `sort_order` как в 4.1, плюс:

| Поле | Тип | NULL | Ограничения | Назначение |
|------|-----|------|-------------|------------|
| `is_apply_channel` | boolean | нет | — | `true`: каналом можно откликнуться (hh.ru, Telegram, почта); `false`: только канал общения (телефон) |

### 4.3. `statuses` — статусы процесса

Поля `id`, `code`, `name_ru`, `sort_order` как в 4.1, плюс:

| Поле | Тип | NULL | Ограничения | Назначение |
|------|-----|------|-------------|------------|
| `kind` | text | нет | `stage` или `outcome` | Этап воронки или итог |
| `stage_order` | smallint | да | Больше 0; уникален; заполнен только у этапов | Порядок этапа (SR11) |
| `is_required_stage` | boolean | да | Заполнен только у этапов | Обязательный этап воронки (SR11) |

### 4.4. `job_processes` — процесс

| Поле | Тип | NULL | Ограничения и ссылки | Назначение |
|------|-----|------|---------------------|------------|
| `id` | bigint, identity | нет | PK | Идентификатор |
| `direction_id` | smallint | нет | FK → `directions` | Направление поиска |
| `initiator` | text | нет | `applicant` или `employer` | Кто начал процесс |

| `vacancy_title` | text | нет | Не пустой | Название вакансии |

| `started_on` | date | нет | — | Дата отклика или первого контакта |
| `vacancy_source_id` | smallint | да | FK → `vacancy_sources`; обязателен для `applicant`, пуст для `employer` | Источник вакансии |
| `apply_channel_id` | smallint | да | FK → `channels`; триггер: только каналы отклика; обязателен для `applicant`, пуст для `employer` | Канал отклика |
| `has_cover_letter` | boolean | да | Обязателен для `applicant`, пуст для `employer` | Сопроводительное письмо |

| `salary_to` | integer | да | Больше 0 | Вилка «до», руб. на руки |

| `communication_channel_id` | smallint | да | FK → `channels`; обязателен для `employer` | Канал общения |
| `contact_name` | text | да | — | Имя контакта |
| `contact_position` | text | да | — | Должность контакта |
| `note` | text | да | — | Комментарий |

## 6. Триггеры

| Триггер | Таблица и событие | Что делает |
|---------|-------------------|------------|
| `job_processes_check_channels` | `job_processes`, до вставки и изменения `apply_channel_id` | Отклоняет канал с `is_apply_channel = false` |
| `process_status_history_check_rejection` | `process_status_history`, до вставки и изменения `status_id`, `rejection_reason_id` | Отклоняет причину отказа у записей, кроме «Отказ работодателя» и «Мой отказ» |
| `process_status_history_sync_status` | `process_status_history`, после вставки, удаления и изменения `status_id`, `recorded_at` | Записывает в `job_processes.status_id` статус последней записи истории (порядок: `recorded_at`, затем `id`) |
| `process_status_history_protect_last` | `process_status_history`, до удаления | Запрещает удалить единственную запись истории процесса; при каскадном удалении процесса (вложенный вызов, `pg_trigger_depth() > 1`) проверка не выполняется |

Порядок работы приложения при создании процесса: в одной транзакции вставить строку
`job_processes` с начальным статусом, затем первую запись истории. Дальше `status_id` вручную не
меняется.

## 7. Индексы

Объём данных мал (3–4 тысячи записей в год, NFR-01), поэтому индексы нужны для ключевых
сценариев, а не для больших нагрузок. Новый индекс добавляется после проверки плана запроса
(`explain analyze`) на демо-данных.

| Индекс | Таблица и поля | Для чего |
|--------|----------------|----------|
| `ix_job_processes_started_on` | `job_processes (started_on desc, id desc)` | Список процессов по дате (US-04) |
| `ix_job_processes_direction_status` | `job_processes (direction_id, status_id)` | Фильтры по направлению и статусу |
| `ix_job_processes_company_title` | `job_processes (lower(btrim(company_name)), lower(btrim(vacancy_title)))` | Проверка дублей (US-02) |
| `ix_job_processes_vacancy_url` | `job_processes (vacancy_url)`, где ссылка задана | Проверка дублей по ссылке |
| `ix_job_processes_autoclose` | `job_processes (started_on)`, где инициатор `applicant` и нет ответа | Отбор кандидатов на автозакрытие (US-11) |
| `ix_status_history_process_recorded` | `process_status_history (process_id, recorded_at, id)` | Последняя запись и история процесса |
| `ix_status_history_status_process` | `process_status_history (status_id, process_id)` | Воронка: кто достиг статуса (US-16) |
| `ix_test_assignments_process` | `test_assignments (process_id)` | Тестовые задания процесса |
| `ix_test_assignments_due_open` | `test_assignments (due_on)`, где не сдано и срок задан | Ближайшие сроки (US-13) |
| `ix_process_skills_skill` | `process_skills (skill_id)` | Рейтинг навыков (US-21) |
| `ix_profile_skills_skill` | `profile_skills (skill_id)` | Обратный поиск по навыку |
| `skills_name_ci_uk` | `skills (lower(name))`, уникальный | Уникальность навыка без учёта регистра |

## 8. Миграции

Схема создаётся нумерованными SQL-файлами в `db/schema/`. Каждый файл применяется один раз,
в одной транзакции, по порядку номеров; применённые файлы не правятся, изменение схемы
оформляется новым файлом (PM-07).

| Файл | Содержание |
|------|------------|
| `001_create_schema.sql` | Справочники, рабочие таблицы, индексы, комментарии |
| `002_seed_reference_data.sql` | Значения справочников (US-14) |
| `003_triggers.sql` | Функции и триггеры (раздел 6) |

Применяет миграции небольшой скрипт на Python: он создаёт служебную таблицу
`schema_migrations` (версия, имя файла, момент применения), запускает ещё не применённые файлы
по порядку и останавливается на первой ошибке. Скрипт описывается отдельно.

## 9. Принятые решения

| ID | Решение |
|----|---------|
| PM-01 | Используется PostgreSQL; версия фиксируется при установке, DDL рассчитан на 14 и новее. База `job_search_crm`, кодировка UTF8, схема `public` |
| PM-02 | Текст хранится типом `text`; идентификаторы формирует СУБД (`generated always as identity`), ручная подстановка запрещена |
| PM-03 | Значения справочников выбираются по полю `code`, а не по числовому `id` |
| PM-04 | Правила выражены ограничениями везде, где это возможно; триггеры только для межтабличных правил (четыре триггера); остальное проверяет приложение и запросы согласованности |
| PM-05 | Текущий статус процесса ведёт триггер (INV-10): приложение указывает только начальный статус при создании процесса |
| PM-06 | Набор индексов минимален (11 индексов и один уникальный по навыкам), обоснован сценариями из историй |
| PM-07 | Миграции: нумерованные SQL-файлы, применяются один раз и не правятся; для изменений создаётся новый файл |
| PM-08 | Словарь данных дублируется в базе комментариями к таблицам и ключевым полям (`comment on`) |

## 10. Открытые вопросы

| ID | Вопрос | Предварительный ответ |
|----|--------|-----------------------|
| PQ1 | Имена базы и роли? | База `job_search_crm`, роль приложения `crm_app` без права создавать базы; пароль хранится в `.env` (NFR-04) |
| PQ2 | Нужны ли служебные поля `created_at` и `updated_at`? | Нет: аудит ведёт история статусов; поля не нужны ни одной истории и усложнили бы форму |
| PQ3 | Где хранятся миграции? | В существующей папке `db/schema/`, новая папка не нужна |
| PQ4 | Какая версия PostgreSQL? | Актуальная стабильная на момент установки; версию проверим по сайту разработчика и запишем в быстрый старт |
| PQ5 | Достаточно ли того, что приложение не меняет `job_processes.status_id` после создания процесса? | Да: статус пересчитывает триггер (PM-05) |
